# Lab Style Guide

This guide documents the conventions of this repo so that any author, human or agent, can create new labs that look and behave like the existing ones. It was produced by auditing the full corpus: five workshop directories (~65 numbered labs), `reference/`, `lib/`, `images/`, the repo meta-files, and the work-in-progress `advanced-scenarios/` lab. Where the repo is internally inconsistent, this guide picks the dominant or best pattern and marks it **normative**.

**TL;DR:** clone the skeleton of `istio-ambient-single-cluster/006-waypoints.md` for a feature lab, `istio-ambient-single-cluster/012-vm-integration-mysql.md` for a lab that ships its own manifests, or `istio-ambient-multicluster/007-segments.md` for a two-cluster lab, then work through the [checklist](#checklist-when-adding-a-lab) at the bottom.

> **If you're a human:** don't try to follow this document by hand; its precision is aimed at agents. Your workflow is three steps: (1) clone the closest existing lab per the TL;DR above, (2) write your content and skim the [checklist](#checklist-when-adding-a-lab), (3) before committing, ask Claude to conform the lab against this guide: it normalizes the mechanical conventions and flags anything that needs your judgment. You own the content; the agent owns the conformance.

## 1. Repo layout

| Path | Purpose |
|---|---|
| `README.md` | Repo index: workshop table, reference table, use-case matrix, versions, prerequisites. Updated for every new lab (§15) |
| `<workshop>/` | One directory per workshop. Six exist: `istio-ambient-single-cluster`, `istio-ambient-single-cluster-on-openshift`, `istio-ambient-multicluster`, `istio-ambient-multicluster-on-openshift`, `istio-oss-sidecar-to-enterprise-ambient`, `istio-ambient-multicluster-nodeport` |
| `<workshop>/README.md` | Workshop index: versions, prerequisites, `## Labs` table, `cd` instruction, reference links |
| `<workshop>/000-introduction.md`, `000-prerequisites.md`, `000-tools.md` | The three `000` files every workshop has: objectives and license check, requirements and image list, tool installs |
| `<workshop>/NNN-<name>.md` | Numbered labs, run in order. The last one is always `NNN-cleanup.md` |
| `<workshop>/bookinfo/`, `auth-policy/`, `grpc/`, `vm/`, `gke/` | Workshop-local manifests applied by relative path (`kubectl apply -f bookinfo/...`) |
| `<workshop>/solo-istioctl`, `shared-root-trust-secret.yaml` | Generated by lab `002` (or `004` in the migration workshop), gitignored, never committed |
| `reference/` | Standalone reference pages that apply to every workshop (`ambient-ports.md`) |
| `lib/` | Repo-level scripts shared across workshops (`mirror-images.sh`); see §11 |
| `images/` | Repo-level diagrams and screenshots, flat, referenced as `../images/<name>.png`. Diagram HTML sources and `render.sh` live beside the PNGs but are gitignored |
| `advanced-scenarios/` | Standalone long-form labs not yet ready for the public repo. Gitignored as a whole |
| `docs/superpowers/{specs,plans}/` | Design docs and implementation plans for substantial labs (§14). Gitignored |

Lab filenames are zero-padded three-digit numbers plus a kebab-case, outcome-descriptive slug: `005-egress.md`, `012-vm-integration-mysql.md`. Numbers are contiguous within a workshop; adding a lab in the middle renumbers everything after it (including the cleanup lab, and every `lab \`NNN\`` cross-reference in prose).

## 2. Lab archetypes

Pick the archetype before writing; conventions differ slightly.

1. **Install or platform lab** (~250–350 lines): `001`–`003` in each workshop. Helm installs with inline values, `rollout status` waits, a `## Validate the installation` section with `kubectl get pods` expected output. Examples: `002-install-istio.md`, `003-enroll-apps-in-the-mesh.md`.
2. **Feature lab** (~180–500 lines): one mesh capability, taught as Background → deploy → verify → (repeat per sub-feature) → Cleanup → Next Steps. Examples: `005-egress.md`, `006-waypoints.md`, `007-segments.md`, `010-grpc-loadbalancing.md`.
3. **Asset-bearing lab**: a feature lab whose manifests are too long or too reusable to inline, shipped in a workshop-local folder (§4). Examples: `011-vm-integration.md` + `vm/`, `012-vm-integration-mysql.md` + `vm/mysql/`.
4. **Narrative or migration lab**: multi-phase runbook with `## Step N — Title` headings and explicit before/after validation. Example: `istio-oss-sidecar-to-enterprise-ambient/005-migrate-namespaces.md`.
5. **Standalone long-form lab** (~1300 lines): self-contained, no `000` dependency, `# Part N` H1 dividers, `## Step N: Title` headings, Troubleshooting, Cleanup and a `## What you built` close. Only `advanced-scenarios/local-dev-against-global-mesh.md` has this shape; use it for a scenario that doesn't fit a workshop sequence.
6. **Reference page** (rare): prose + tables, no hands-on skeleton, opens with a `**Reference page.**` bold lead. Example: `reference/ambient-ports.md`.

The three `000` files and the `NNN-cleanup.md` file are fixed shapes, not archetypes to choose from; copy them from a sibling workshop (§3.1, §10).

## 3. Canonical lab skeleton (normative)

```markdown
# <Outcome-Oriented Title in Title Case>

# Objectives
- <verb-first outcome bullets, naming resources in backticks>

![](../images/<lab-slug>-1.png)        <- optional; diagram or screenshot for the lab

## Prerequisites
- This lab assumes you have completed setup from labs `000-00N`
- <extra deps: namespace enrolled, Docker-based cluster, optional CLI>

Ensure the following environment variables are set:
```bash
export KUBECONTEXT_CLUSTER1=cluster1  # Replace with your actual kubectl context name
```

## Background                      <- the "why": prose, comparison table, ASCII or PNG diagram

## <Feature section>               <- each: prose "why" → command block → verify → expected output
## <Feature section>

## Cleanup                         <- lab-scoped teardown (§10)

## Next Steps
At this point we have completed the following objectives:
- <restate the Objectives bullets in past tense>

In the next step `00N+1` we will <one sentence>.
```

Rules:

- **Title**: H1, Title Case, describes the outcome, no lab number. Verb-first (`# Expose Bookinfo`, `# Add a VM Workload to the Mesh`) or noun-phrase with a dash qualifier (`# Segments — Namespace Isolation Across Clusters`) are both established; verb-first preferred for new labs.
- **`# Objectives` is an H1**, not H2. This is an established repo quirk (64 of 65 labs); keep it. Bullets are verb-first outcomes. Optional parts are marked `(Optional)` at the start of the bullet.
- **Prerequisites boilerplate** (use verbatim, varying only the range): *"This lab assumes you have completed setup from labs `000-00N`"*. Install labs use *"This lab assumes you have read through and completed any setup from the `000` labs"*. Labs with hard dependencies on a specific earlier lab add a second bullet saying what must be running (*"The `bookinfo-backends` namespace must be enrolled in ambient mesh"*). Labs that can be skipped by the reader open with a blockquote gate: `> **Skip this section if you did not complete lab `009`.**`
- **Lab cross-references** in prose use the bare backticked number: ``lab `002` ``, ``labs `000`–`004` ``. Reference labs in other directories or other workshops with relative markdown links (`[single-cluster version of this lab](../istio-ambient-single-cluster/010-grpc-loadbalancing.md)`).
- **Environment variables** come right after Prerequisites, under either the inline sentence *"Ensure the following environment variables are set:"* (feature labs) or a `## Set environment variables` section (install labs). Multicluster labs call it `## Set cluster contexts`. Always re-export `KUBECONTEXT_CLUSTER1` (and `_CLUSTER2`) with the trailing comment, even though an earlier lab already set it: each lab is pasteable from a fresh shell.
- **`## Background`** is the standard "why" section (25 labs). It explains the mechanism before any command, often with a comparison table (`| Setting | Single-cluster effect | Why it matters for multicluster |`) or a role table (`| Container | Plays the role of |`).
- **Step headings**: feature labs use plain descriptive `##`/`###` Title Case headings. Migration runbooks use `## Step N — Title` (em-dash). The standalone advanced lab uses `## Step N: Title` with `# Part N` H1 dividers and `---` rules. For a new numbered runbook inside a workshop, use the em-dash form.
- **`## Next Steps`** (52 labs) closes every lab except cleanup: *"At this point we have completed the following objectives:"*, the Objectives restated in past tense, then *"In the next step `NNN` we will ..."*. A lab that is the end of a phase may lead with `**Phase 2 (Migration) is complete.**`.
- **Validated-against statements** belong in the workshop `000-introduction.md` `## Validated on` list, not in individual labs. Labs that only work on a specific platform say so in Prerequisites (*"A Docker-based local cluster (vind or KinD)"*) and point readers elsewhere for other platforms.

### 3.1 The `000` files

Every workshop has the same three, kept in lockstep across workshops:

- **`000-introduction.md`**: H1 workshop title, `# Objectives` (H1), `# Use Cases` (H1, matches the README use-case matrix), `## Validated on`, `## License Key Details` with the verbatim license-expiry bash snippet (copy it from a sibling; it decodes `SOLO_TRIAL_LICENSE_KEY` and works on both GNU and BSD `date`).
- **`000-prerequisites.md`**: numbered list (license key, `solo-istioctl`, `helm`, `kubectl`, Kubernetes version, `openssl`, optional tools, lab-specific extras marked `(Labs `011` and `012` only)`), then `### Repos/Images` with the `> **Air-gapped clusters:**` callout pointing at `lib/mirror-images.sh`, `**Helm Repos**` (`helm pull oci://...`) and `**<Group> Images:**` (`docker pull ...`) blocks. `lib/mirror-images.sh` parses the `docker pull` lines in this file, so every image a lab uses must appear here as a plain `docker pull <image>:<tag>` line.
- **`000-tools.md`**: `# TOOLING AND TROUBLESHOOTING`, `#### Solo's `istioctl` Binary` download block, `## Optional Tools` (K9s, Vegeta, Fortio), `## Troubleshooting Resources`.

## 4. Asset-bearing labs

Manifests live in a workshop-local folder when they are long, reused by several labs, or applied and deleted symmetrically. Established folders: `bookinfo/` (app manifests, shared by every lab), `auth-policy/` (one file per AuthorizationPolicy), `grpc/`, `vm/`, `vm/mysql/`, `gke/`.

- Apply with a path relative to the workshop directory, never `cd` and never `$REPO_ROOT`: `kubectl apply -f bookinfo/bookinfo-backends.yaml --context $KUBECONTEXT_CLUSTER1`. The workshop README says to `cd <workshop>` first, and `./solo-istioctl` relies on it.
- Delete the same file in cleanup: `kubectl delete -f bookinfo/bookinfo-waypoint-services.yaml --context $KUBECONTEXT_CLUSTER1 --ignore-not-found`.
- One manifest per file for policies (`auth-policy/details-auth.yaml`); multi-document files joined with `---` for an app or a client set (`vm/mysql/db-clients.yaml`: Namespace, ServiceAccounts, Deployments).
- Short, lab-specific manifests (a Gateway, an HTTPRoute, a Telemetry resource, a single policy) are inlined as heredocs instead (§6). The repo prefers inline when the reader needs to see the YAML to learn from it.
- **Secrets and generated artifacts** are gitignored by pattern, not by exception: `*-secret.yaml`, `*.pem`, `*.key`, `**/solo-istioctl`, `**/vm-tokens/`, `**/vm-db-tokens/`. A new lab that generates credentials or tokens adds its directory to `.gitignore` with a one-line comment naming the lab (`# VM MySQL lab (012): bootstrap and workload tokens are credentials`).
- Workshop-only credentials baked into a manifest (a MySQL root password, an app user) are fine but must be stated as such in the lab prose.
- Each sibling workshop keeps its own copy of shared folders (`bookinfo/`, `auth-policy/`); they are not symlinked. When you change one, change the siblings (§16).

## 5. Tone and voice

- Second person, imperative, present tense: "Label the namespace...", "Send a request through the ingress gateway". "We" appears in `## Next Steps` ("At this point we have completed...") and occasionally in verification prose ("we also need the backend services").
- **Why-first**: every non-trivial config gets a rationale *before* the command. Vehicles: `## Background`, a sentence immediately above the fence, a `> **Why ...?**` blockquote at the point of a surprising choice, or a comparison table. The strongest labs name what breaks without the setting and what the symptom looks like (*"Mismatching these causes ztunnel to fail VIP lookups, silently bypassing waypoints."*).
- Teach from real output. Labs paste genuine ztunnel log lines or metric samples and then explain them field by field under `### Reading the log fields` or bold inline leads (`**`src.identity` and `dst.identity`** — ...`). Expected output comes from a real run; the newest labs record where (vind on Docker Desktop, arm64).
- Call out gotchas at the exact step where they bite, as a bold-lead blockquote (`> **KinD users:**`, `> **GKE only:**`, `> **zsh users:**`).
- Be explicit about production hygiene when a lab relaxes something: say what the setting weakens, that it is workshop-only, and which lab removes it (*"Keep this setting out of production clusters. It stays in place until lab `013` uninstalls Istio."*).
- **Em dashes**: the older labs use them freely (titles, callouts, explanations). The newest labs (`011`, `012`, `advanced-scenarios/`) were written with zero em dashes and plain sentences. New labs follow the newer style: no em dashes in prose, headings, or diagram labels. Don't rewrite existing labs for this alone.
- No marketing voice. Say what Solo adds where it matters with the `> **Solo Enterprise feature:**` or `> **Solo Enterprise guidance:**` callout, then move on.

## 6. Command-block conventions

All commands use ```` ```bash ```` fences. Manifests are applied inline via heredoc inside the bash fence, not in separate `yaml` fences (the one exception is a YAML *fragment* shown for substitution, as in the TLS-listener note in `004-expose-bookinfo.md`).

**The `--context` flag is on every `kubectl` command** and `--kube-context` on every `helm` command, always as `$KUBECONTEXT_CLUSTER1` / `$KUBECONTEXT_CLUSTER2`. Never rely on the current context. Multicluster labs that do the same thing on both clusters loop: `for context in $KUBECONTEXT_CLUSTER1 $KUBECONTEXT_CLUSTER2; do ... --context $context; done`.

**Heredoc forms (normative):**

- `kubectl apply --context $KUBECONTEXT_CLUSTER1 -f - <<EOF` (space before `<<`) for manifests. This is the dominant form (117 uses).
- `helm upgrade ... -f -<<EOF` (no space) for Helm values. Also dominant (26 uses) and distinct from the kubectl form; keep the split.
- Unquoted `<<EOF` is the default because values interpolate `$ISTIO_VERSION`, `$MESH_NAME_CLUSTER1`, `$SOLO_TRIAL_LICENSE_KEY`. Quote the delimiter (`<<'EOF'`, `<<'CNFEOF'`) only when the body must not expand (openssl config files, scripts with their own `$`). Use a distinct delimiter such as `CNFEOF` when nesting a heredoc inside a block that already uses `EOF`.

**The universal idioms (copy these verbatim):**

Context and mesh name:

```bash
export KUBECONTEXT_CLUSTER1=cluster1  # Replace with your actual kubectl context name
export MESH_NAME_CLUSTER1=cluster1    # Recommended to keep as cluster1 for POC
```

License guard (install labs only):

```bash
export SOLO_TRIAL_LICENSE_KEY=$SOLO_TRIAL_LICENSE_KEY
[ -n "$SOLO_TRIAL_LICENSE_KEY" ] || echo "⚠️  SOLO_TRIAL_LICENSE_KEY is not set. Istio installs with an empty license and enterprise features, including multicluster peering, then fail."
export ISTIO_VERSION=1.30.5
```

Idempotent namespace creation:

```bash
kubectl create namespace istio-eastwest --context $KUBECONTEXT_CLUSTER1 --dry-run=client -o yaml | kubectl apply --context $KUBECONTEXT_CLUSTER1 -f -
```

Wait for a rollout (always bounded):

```bash
kubectl rollout status deploy/istiod -n istio-system --watch --timeout=90s --context $KUBECONTEXT_CLUSTER1
kubectl wait --for=condition=Programmed gateway/istio-eastwest -n istio-eastwest --timeout=120s --context $KUBECONTEXT_CLUSTER1
```

Ingress address with the no-LoadBalancer fallback:

```bash
SVC=$(kubectl -n istio-system get svc ingress-istio --context $KUBECONTEXT_CLUSTER1 --no-headers | awk '{ print $4 }')
if [[ "$SVC" == "<pending>" || -z "$SVC" || "$SVC" == "<none>" ]]; then
  echo "⚠️  No external LoadBalancer IP available. See the 'No LoadBalancer? Use Port-Forward' section below."
else
  echo http://$SVC/productpage
fi
```

Background port-forward with cleanup:

```bash
kubectl port-forward -n istio-system $ZTUNNEL_POD 15020:15020 --context $KUBECONTEXT_CLUSTER1 &
PORT_FORWARD_PID=$!
sleep 2
# ... curl ...
kill $PORT_FORWARD_PID
```

Pick the ztunnel on the same node as the workload (ztunnel is per-node; any other pod returns nothing):

```bash
APP_NODE=$(kubectl get pod -n bookinfo-frontends -l app=productpage \
  --context $KUBECONTEXT_CLUSTER1 -o jsonpath='{.items[0].spec.nodeName}')
ZTUNNEL_POD=$(kubectl get pods -n istio-system -l app=ztunnel \
  --field-selector spec.nodeName=$APP_NODE \
  --context $KUBECONTEXT_CLUSTER1 -o jsonpath='{.items[0].metadata.name}')
```

Helm install shape (every Istio chart):

```bash
helm upgrade --kube-context $KUBECONTEXT_CLUSTER1 --install istiod \
  oci://us-docker.pkg.dev/soloio-img/istio-helm/istiod \
  -n istio-system \
  --version=$ISTIO_VERSION-solo \
  -f -<<EOF
profile: ambient
global:
  hub: us-docker.pkg.dev/soloio-img/istio
  tag: $ISTIO_VERSION-solo
  variant: distroless
EOF
```

Post-install tweak to an existing release (don't repeat the whole values file):

```bash
helm upgrade --kube-context $KUBECONTEXT_CLUSTER1 istiod oci://us-docker.pkg.dev/soloio-img/istio-helm/istiod \
  -n istio-system --version 1.30.5-solo --reuse-values --set-string env.REQUIRE_3P_TOKEN=false
```

**Env vars**: `SCREAMING_SNAKE_CASE`, exported. Fixed names: `KUBECONTEXT_CLUSTER1/2/3`, `MESH_NAME_CLUSTER1/2/3`, `ISTIO_VERSION` (bare `1.30.5`; charts append `-solo`), `SOLO_TRIAL_LICENSE_KEY`, `SOLO_MANAGEMENT_UI_VERSION`, `SOLO_MANAGEMENT_UI_OCI_REPO`, `CLUSTER1_EW_ADDRESS` / `CLUSTER1_EW_ADDRESS_TYPE`. Placeholder guidance goes in the trailing comment. Multi-line explanations of a variable go as `#` comment lines above it inside the fence (see the `MESH_NAME_CLUSTER1` comment in the Solo UI lab).

**Version pins**: lab prose and `000-prerequisites.md` hardcode the full version (`1.30.5-solo`, `0.5.8`); install commands use `$ISTIO_VERSION-solo`. A version bump touches every workshop's prerequisites, introduction, README, the root README, and every hardcoded `--version` (§15).

**Platform-conditional commands** go in a blockquote with their own fence: `> **GKE only:** ... > ```bash ... > ```` (the `gke/resourcequota.yaml` step). Values that a platform user must uncomment are left as `#` comment lines in the values heredoc with a `> **GKE users:** Uncomment ...` note above the block.

**curl conventions**: `curl http://$SVC/productpage -s -o /dev/null -w "%{http_code}"` for status checks; `curl ... | grep -o "<title>.*</title>"` to prove a page rendered; `-v` or `-i` when headers are the evidence (waypoint `server: istio-envoy`). Prefer curl over a browser for log-observation steps and say why (the `> **Why curl and not a browser?**` callout).

## 7. Verification and expected output

Every mutating step is immediately followed by a check. Two accepted styles:

1. **`Expected output:`** label + unlabelled fenced block (29 uses; use this exact casing). Qualify in parentheses when needed: `Expected output (abridged):`, `Expected output (the address differs on your machine):`, `Expected output (HBONE — enrolled in ambient mesh):`. Paste real output with real pod suffixes; replace only genuinely environment-specific values with `<external-ip>` style placeholders.
2. Prose assertion for simple cases: *"You should see `200` printed in your terminal"*, *"Both should return `HTTP 200`"*.

Standard verification tools:

- `kubectl get pods -n <ns>` with expected output after every install or enrollment.
- **ztunnel logs** are the primary zero-trust evidence: `kubectl logs -n istio-system -l app=ztunnel --context $KUBECONTEXT_CLUSTER1 -f --prefix` in a second terminal, then explain `src.identity`, `dst.identity`, `dst.hbone_addr`, `direction`, and `policy rejection` lines.
- `./solo-istioctl ztunnel-config workloads` (or `zc`) to show `PROTOCOL` flipping from `TCP` to `HBONE` on enrollment; `./solo-istioctl waypoint`, `./solo-istioctl proxy-status`, `./solo-istioctl multicluster check`.
- Metrics by port-forwarding `15020` (ztunnel) or `15014` (istiod) and `curl /metrics | grep ...`.
- Negative tests are first-class: show the request *succeeding* before the policy and *failing* after it, and show the matching `policy rejection` log line. Add a `sleep 3` after applying a policy before testing when propagation can race.
- Idempotence: blocks a learner may re-run (token extraction, `docker rm -f`, `--dry-run=client | apply`) must be safe to repeat, and the lab says so when it matters.

## 8. YAML manifest conventions

- **Namespaces**: `istio-system` for the control plane, gateways and `cacerts`; `bookinfo-frontends` / `bookinfo-backends` for the app; `egress` for the egress waypoint and ServiceEntries; `istio-eastwest` for the east-west gateway; `kagent` for the Solo Management UI; `grpcdemo`, `vm-apps`, `vm-db`, `db-clients` for the add-on labs. Ambient enrollment is the namespace label `istio.io/dataplane-mode=ambient`.
- **The stable resource set**: `gateway.networking.k8s.io/v1` `Gateway` (class `istio` for ingress, `istio-waypoint` for waypoints, listener `mesh` on `15008`/`HBONE`) and `HTTPRoute`; `security.istio.io/v1` `AuthorizationPolicy`; `networking.istio.io/v1` `ServiceEntry` and `VirtualService` (only where Gateway API has no equivalent, such as fault injection); `telemetry.istio.io/v1` `Telemetry`; Solo `Segment` CRs in the multicluster workshops.
- **Naming**: the ingress Gateway is `ingress` (service `ingress-istio`), the namespace waypoint is `waypoint`, the main route is `bookinfo-route`. Policies are `<target>-auth` or `<purpose>-<scope>` (`jsonplaceholder-egress`, `waypoint-access-logging`). Keep names identical across sibling workshops.
- **Policies target by `targetRefs`** (Gateway, Service, or ServiceEntry), not `selector`, wherever ambient supports it. Principals are full SPIFFE paths with the per-cluster trust domain: `cluster1.local/ns/bookinfo-backends/sa/bookinfo-reviews`.
- **Gateway API ingress customization** (cloud LB annotations, TLS listeners) is shown as an alternative in a `> **Note:**` blockquote with its own fenced heredoc, not as the default path.
- **Comment style in values heredocs**: plain `#` explanatory comments on the line above the key (`# Required when clusters have distinct trust domains`). Optional overrides are left as commented-out blocks with a `# override (...)` or `# uncomment if using GKE` header. Private-registry image overrides appear as commented `#global: #  image:` blocks in the Solo UI lab; keep that pattern for any new chart.
- **Helm values that are production-unsafe** get a comment saying so and which lab removes them (`# Remove this block for production deployments.`).

## 9. Callouts, tables, diagrams, images

- **Callouts (normative)**: bold-lead blockquotes, `> **Note:** ...` being the most common (29). Audience-scoped leads are the house pattern: `> **KinD users:**`, `> **GKE users:**`, `> **GKE only:**`, `> **Private registry users:**`, `> **Air-gapped clusters:**`, `> **OpenShift ambient probes:**`, `> **zsh users:**`. Other established leads: `> **Why ...?**`, `> **Important:**`, `> **Keep this file.**`, `> **Reference:**`, `> **Troubleshooting:**`, `> **Solo Enterprise feature:**`. A lead may be a full bold sentence ending in a period when the warning is the whole point (`> **Takeover applies to every caller.**`). GitHub alert syntax (`> [!NOTE]`) is not used anywhere; don't introduce it.
- **Diagrams**: PNGs in `images/`, placed directly under `# Objectives`, referenced as `![](../images/<slug>-1.png)` with no alt text. Sources are hand-written HTML next to the PNG and rendered with `images/render.sh` (headless Chrome, 2x scale); both are gitignored, only the PNG is committed. Add a size entry to `render.sh` for a new diagram. ASCII diagrams in fenced blocks are acceptable for small flows. No mermaid anywhere in the repo; keep it that way.
- **Screenshots**: numbered `<slug>-N.png` (`waypoints-1.png` ... `waypoints-7.png`, `solo-ui-1.png`), used for UI-heavy steps (Solo Management UI, Kiali-style views). Single-cluster variants of a multicluster diagram get a `-singlecluster-` infix.
- **Tables**: GitHub pipe tables for comparison matrices, role mappings, port references, log-field explanations, and results summaries. Reference pages are mostly tables.
- Collapsible `<details>` blocks are not used; keep deep-dives as `###` sub-sections.

## 10. Cleanup (normative)

Two layers:

1. **Per-lab `## Cleanup`** (30 labs), placed before `## Next Steps`, removes only what *this* lab created and restores anything it mutated: delete the route and policies, `kubectl delete -f` the lab's manifests, `kubectl patch` the Service selector back, unlabel the namespace (`istio.io/use-waypoint-`), delete the waypoint Gateway. A sentence of prose introduces each block. Use `--ignore-not-found` on every delete (newer labs do; older ones don't; follow the newer style). State when a lab leaves something in place on purpose and which lab removes it.
2. **The workshop `NNN-cleanup.md`** is the last lab: one `##` section per earlier lab or subsystem, in reverse dependency order (Solo UI → gateways and routes → app namespaces → add-on labs by number → `helm uninstall` of ztunnel, istiod, istio-cni, istio-base → delete `istio-system`), closing with the `./solo-istioctl uninstall --purge -y` alternative. Add-on labs that run outside the cluster also remove local state (`docker rm -f ...`, `rm -rf ./vm-tokens ./vm-config`). Every new lab adds a section here, titled with its number: `## MySQL on a VM (lab `012`)`.

```bash
kubectl delete virtualservice reviews-fault -n bookinfo-backends --context $KUBECONTEXT_CLUSTER1 --ignore-not-found
kubectl delete httproute reviews -n bookinfo-backends --context $KUBECONTEXT_CLUSTER1 --ignore-not-found
kubectl delete -f bookinfo/bookinfo-waypoint-services.yaml --context $KUBECONTEXT_CLUSTER1 --ignore-not-found
kubectl patch svc reviews -n bookinfo-backends --context $KUBECONTEXT_CLUSTER1 \
  --type=merge -p '{"spec":{"selector":{"app":"reviews","version":null}}}'
```

## 11. Shared assets (`lib/`) and non-Kubernetes steps

- `lib/` holds repo-level scripts that serve every workshop, not lab manifests. The one resident, `lib/mirror-images.sh`, is the model: a long header comment (purpose, usage, examples, what it never does, requirements), `set -uo pipefail`, a `usage()` that prints the header, dry-run by default with an explicit `--push`. It derives its input from the labs (`docker pull` lines in `000-prerequisites.md`) rather than a second list that can drift.
- Labs reference `lib/` from the repo root in the `000-prerequisites.md` callout: *"Run it from the repo root"*, with a relative link `[`lib/mirror-images.sh`](../lib/mirror-images.sh)`.
- **Host-side steps use bash and coreutils only**: no python, no jq, no yq. Decode and parse with `base64`, `sed`, `awk`, `tr`. The license-expiry snippet in each `000-introduction.md` is the reference for portable bash (handles GNU and BSD `date`).
- **"VM" labs** run the VM as containers on the cluster's Docker network (`--network container:<vm>`), with a role table explaining the mapping to a real VM (`docker exec` ↔ `ssh`, `docker cp` ↔ `scp`). Tokens and generated config go in gitignored `./vm-*` directories under the workshop folder. Onboarding uses `./solo-istioctl vm add-workload`.
- **Load generation** is optional and uses Vegeta or Fortio from `000-tools.md`, run from the laptop, never a k6 Job.
- Scratch files: the repo uses `$(mktemp -d)` plus `rm -rf "$WORK_DIR"` inside one block for cert generation; everything the reader keeps is written into the workshop directory (`shared-root-trust-secret.yaml`, `./vm-tokens`). Don't leave artifacts in `/tmp`.

## 12. Observability section

Observability is its own lab per workshop (`007-observability.md` in single-cluster, `011-observability.md` in multicluster), not a per-lab block. Feature labs that want to show telemetry do it inline with the ztunnel-log or `/metrics` idioms from §6 and §7, then point at the observability lab rather than repeating it.

Conventions inside the observability labs:

- `## Background` with the component/port/path table (ztunnel `15020`, istiod `15014`).
- `## ztunnel Metrics (L4 + L7)` and `## istiod Metrics` sections; `(Optional)` PodMonitor section for persistent scraping.
- ztunnel runs with `L7_ENABLED: "true"` (set in the install lab), so L7 request metrics come from ztunnel without a waypoint; say so.
- OpenShift variants use User Workload Monitoring instead of a PodMonitor-only path, and the OCP observability lab has its own screenshots (`ocp-observability-*.png`).
- Tracing is a separate lab (`008-tracing.md`) in the single-cluster workshop only.

## 13. Workshop-variant conventions

The six workshops are **siblings that share lab bodies**. The single-cluster and OpenShift single-cluster `004-expose-bookinfo.md` files are byte-identical for their first sixty lines, and the multicluster pair shares most content. The established pattern is clone-and-substitute with an explicitly scoped delta:

- **OpenShift variants** differ only where the platform forces it: `oc adm policy add-scc-to-group anyuid system:serviceaccounts:<ns>` before deploying Bookinfo, an SCC for ClickHouse in the Solo UI lab, OpenShift `Route` for exposure, User Workload Monitoring for observability, and the `> **OpenShift ambient probes:**` note. Everything else is copied verbatim from the Kubernetes sibling. Keep `kubectl` as the CLI; use `oc` only for OpenShift-only verbs.
- **Multicluster variants** add `KUBECONTEXT_CLUSTER2`, `MESH_NAME_CLUSTER2`, a `## Set cluster contexts` section, `for context in ... do` loops, and the `cluster1.local` / `cluster2.local` trust-domain split. The single-cluster install is deliberately multicluster-ready (`PILOT_SKIP_VALIDATE_TRUST_DOMAIN`, `platforms.peering.enabled`, per-cluster trust domain) and its Background table explains why; preserve that so a single-cluster install can grow into the multicluster workshop.
- **The migration workshop** starts from OSS Istio (`OSS_ISTIO_VERSION`) and its introduction is a `## Three-Phase Journey` with `### Phase N — Title (Labs 00A–00B)` headings. Its `envoyfilter/envoyfilter-migration.md` is an unnumbered side lab with a two-workshop prerequisite line.
- When a lab exists in several workshops, **a fix in one is a fix in all**: grep the siblings for the same heading or command and apply the change everywhere in the same CHANGELOG version. Labs that exist in only one workshop (VM integration, tracing, gRPC takeover, third cluster) are listed in the README use-case matrix with a single tick.
- A lab that mirrors a sibling but on a different platform links to it: *"See the [single-cluster version of this lab](../istio-ambient-single-cluster/010-grpc-loadbalancing.md)"*.

## 14. Development workflow for substantial labs

For a substantial new lab, the repo workflow is brainstorm → spec → plan → live spike → write → validate:

- `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`: `# Lab NNN: <title> (design)`, then `## Goal` with explicit **success criteria** (what each client gets, what the ztunnel log must show, which platform the expected output was captured on), `## Constraints`, `## Topology and names` table, `## Steps`, `## Files`.
- `docs/superpowers/plans/YYYY-MM-DD-<topic>.md`: opens with the `> **For agentic workers:**` sub-skill line, `**Goal:** / **Architecture:** / **Tech Stack:** / **Spec:**` bold leads, `## Global Constraints`, `## Review Focus` (numbered risks, each pinned to the task step that tests it), then checkbox tasks (`- [ ]`). Task 1 is a **throwaway spike on a live cluster** that proves the risky parts and captures real output before any prose is written.
- Both directories are gitignored. They are working artifacts, not deliverables.
- Validate the finished lab end to end on a fresh cluster (vind, KinD, or a cloud cluster) before changing the README matrix. Re-run every block twice where idempotence matters.

## 15. Repo maintenance when adding a lab

**The workshop README table, the workshop `000` files, the root README, the cleanup lab and a CHANGELOG entry are all required for every new lab, not optional cleanup.** A lab isn't done until all are updated in the same change.

**`<workshop>/README.md`**: add a row to `## Labs` (`| [NNN-name.md](NNN-name.md) | Short topic |`), renumbering later rows if you inserted mid-sequence. Add any new prerequisite to `## Prerequisites`.

**`<workshop>/000-introduction.md`**: add an Objectives bullet and a Use Cases bullet; extend `## Validated on` if the lab needs a specific platform (*"vind on Docker Desktop (arm64) for labs `011` and `012`"*).

**`<workshop>/000-prerequisites.md`**: add numbered-list items for new tools, scoped `(Lab `NNN` only)`, and a `docker pull` line for every new image under a labelled `**<Group> Images (lab `NNN`):**` block. `lib/mirror-images.sh` reads these lines.

**`<workshop>/NNN-cleanup.md`**: add a `## <Topic> (lab `NNN`)` section; renumber the file if the new lab displaced it.

**Root `README.md`**: update the workshop's description cell in `## Workshops`, add or tick a row in `## Use Cases Covered`, and bump `## Versions` if versions changed. A new reference page gets a row in `## Reference`.

**`images/`**: add the diagram PNG (and its gitignored HTML source plus a `render.sh` size entry).

**`.gitignore`**: add any generated credential or token directory with a comment naming the lab.

**CHANGELOG.md + commit**:

- Open a new version block at the top: `X.Y.Z - (M-D-YY)` followed by a `---` underline. Patch bump for a single lab or fix; minor bump for a batch of labs or a structural change.
- Bullets lead with `Add`/`Update`/`Bump`/`Move` and name touched files or workshops in backticks: ``- Add `lib/mirror-images.sh` to copy each workshop's prerequisite images ...``. A version bump bullet lists every place it touched in parentheses.
- Commit message is exactly `see CHANGELOG (X.Y.Z)`, with the CHANGELOG block pasted as the body: one commit per changelog version; all descriptive detail lives in the CHANGELOG. Don't commit unless asked; leave the work uncommitted for review.

## 16. Known inconsistencies (and what to do)

These exist in the corpus; new labs should follow the **normative** column.

| Drift observed | Normative choice for new labs |
|---|---|
| `# Objectives` (H1) in 64 labs vs `## Objectives` in one | `# Objectives` (H1), matching the corpus |
| `labs `000-004`` vs `labs `000`–`004`` in the prerequisites sentence | Either; prefer the hyphenated single backtick form `labs `000-004`` used by most labs |
| `## Step N — Title` (migration workshop) vs `## Step N: Title` (advanced scenario) vs unnumbered | Unnumbered `##` for feature labs; `## Step N — Title` for numbered runbooks inside a workshop |
| Em dashes everywhere in older labs vs none in `011`, `012`, `advanced-scenarios/` | No em dashes in new labs; leave old labs alone |
| Cleanup with/without `--ignore-not-found` | Always `--ignore-not-found` |
| `Expected output:` vs `Expected output for pods:` vs sentence-form labels | `Expected output:` with an optional parenthetical qualifier |
| `>= 1.29` vs `≥ 1.29` in README version tables | `≥ 1.29` (the root README and newer workshop READMEs) |
| Hardcoded `--version 1.30.5-solo` vs `$ISTIO_VERSION-solo` | `$ISTIO_VERSION-solo` in install labs; hardcoded full version is tolerated in later labs that tweak a release with `--reuse-values`, but both must be bumped together |
| `kubectl rollout status deploy/...` vs `deployment/...` | `deploy/` (74 vs 23) |
| `000-tools.md` anchor links to `#solos-1250-istioctl-binary` | Stale anchor from an old heading; new links use `#solos-istioctl-binary` and the heading should not embed a version |
| Workshop-local copies of `bookinfo/` and `auth-policy/` drifting between siblings | Diff against the sibling before editing; apply changes to all copies |

Also watch for: lab renumbering leaving stale ``lab `NNN` `` references in prose, README tables, cleanup section titles and `.gitignore` comments; `000-prerequisites.md` image lists lagging a lab's actual images (which silently breaks `lib/mirror-images.sh`); the root README `## Versions` lagging the install labs; and the `## Next Steps` closing sentence pointing at the wrong next lab after an insert.
